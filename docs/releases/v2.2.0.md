# Tor Guard Relay v2.2.0

A security-focused update with safer release promotion, clearer operator diagnostics and encrypted recovery.

> **Update Tor promptly.** Tor 0.4.9.14 fixes high-severity security issues affecting all components. Images built from this source require Tor 0.4.9.14 or newer. Recreating a relay from the validated image is necessary; editing torrc alone does not update Tor. See the [upstream security announcement](https://forum.torproject.org/t/security-release-0-4-9-14/22241).

## What changed

Upstream's [tagged changelog](https://gitlab.torproject.org/tpo/core/tor/-/blob/tor-0.4.9.14/ChangeLog) fixes a Conflux assertion, MiddleOnly flag handling, family-certificate expiry and circuit timeout/connection recovery behavior, among other fixes. These are Tor fixes carried by the updated image, not new container features.

- Stable images use Alpine 3.24.2 with a pinned base digest. Both stable and edge enforce the Tor security floor.
- Lyrebird is built from a pinned revision with a checked-in Go dependency graph, including Pion STUN 3.1.7. The Go builder is pinned to 1.27.2.
- Health separates process liveness, config validity, bootstrap readiness and observation freshness. Old logs cannot mark a restarted relay ready.
- `doctor` explains reason codes; `bridge-line` reports transport state and accepts an explicit public address.
- Generated configuration is validated before atomic replacement. Mounted torrc files remain authoritative. New accounting and IPv6 ENV options cover common operator settings.
- `refresh` validates and signals one exact Tor process. Shutdown forwards SIGTERM with a bounded wait and preserves natural process failures.
- Host-only backup creates encrypted archives containing active config/includes, complete identity/state and an integrity manifest. Verification authenticates every member; restore stages into a new directory and validates configuration offline.
- Host inventory exports local fleet JSON and Prometheus text without opening a monitoring port.
- Release automation builds and validates each stable/edge AMD64/ARM64 candidate once, then promotes those images. Security floors and scan policy block promotion while retaining the full report. Curated notes replace raw commit dumps; registry retention produces a read-only inventory for manual review.

## Compatibility and migration

| Area | Earlier behavior | v2.2.0 |
| --- | --- | --- |
| Health | Bootstrap evidence could outlive a run | Explicit current-run freshness and readiness |
| Config | Generated and mounted ownership could drift | Validation before atomic publication; mounted source remains authoritative |
| Recovery | Separate key copies and plaintext examples | Encrypted complete recovery set with full verification and staged restore |

Existing official bridge ENV aliases and Happy Family settings remain supported. Existing health fields remain available; `reachable` stays a string. New consumers should use the boolean fields and reason codes.

Generated torrc files are regenerated from ENV on restart. Persist operator-applied changes in deployment ENV or use a mounted torrc. Mounted config and include paths must be present in the container. For readiness, retain notice logging at the configured notice path.

Backups require host Python 3.10+ and age. Restore requires a compatible local image and a new staging directory. Unsupported include layouts or source links fail closed. Offline/external master keys require separate recovery material.

Legacy emergency/validator/test scripts that used plaintext archives or live-volume replacement are retired. The interactive migration assistant requires recipient and recovery-identity paths and aborts if encrypted backup verification fails.

## Operator upgrade checklist

1. Record current fingerprint, image digest and deployment.
2. Create and verify an encrypted backup; rehearse staging restore.
3. Review mounted config or generated ENV ownership and validate the deployment.
4. Recreate with the validated v2.2.0 image after it is published.
5. Confirm unchanged fingerprint, current Tor version and fresh bootstrap evidence.
6. Check public reachability separately. Retain the previous image and deployment for rollback.

## Validation scope

Local acceptance uses network-disabled synthetic guard, exit and bridge fixtures. It checks configuration, reload, restart freshness, transport state and shutdown. It does not claim live network bootstrap, consensus participation, production migration, registry promotion or website publication. Detailed build and recovery evidence belongs in the local release handoff.
