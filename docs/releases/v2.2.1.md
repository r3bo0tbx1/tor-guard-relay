# 🧅 Tor Guard Relay v2.2.1

Tor 0.4.9.15 security update: directory-request DoS defenses and an identity-preserving upgrade.

> [!IMPORTANT]
> **Upgrade required:** Every relay and bridge operator should upgrade to a validated image with Tor **0.4.9.15 or newer** as soon as possible. Tor's [tagged changelog](https://gitlab.torproject.org/tpo/core/tor/-/blob/tor-0.4.9.15/ChangeLog), dated **28 October 2026**, calls this a security release primarily affecting relays. Recreate the container and verify the running binary; changing torrc alone does not upgrade Tor.

## 🛡️ What Tor changed

| Change | Operator impact |
| --- | --- |
| Per-circuit BEGIN_DIR rate limit | Enabled by default for directory caches, including relays and bridges. Keep consensus-controlled settings unset. |
| One BEGIN_DIR per circuit arriving from an authenticated relay | Controlled only by the network consensus; initially disabled. Do not add `DoSBeginDirLimitEnabled` to torrc or try to enable this independently. |
| One HSDir descriptor request per circuit from an authenticated relay | A later descriptor fetch/upload on the same circuit closes it, even while the preceding consensus limit is disabled. |
| Sticky HSDir flag | An authority can retain the flag across a restart when the relay held it in a recent consensus. Initial eligibility still requires 96 hours of uptime; leaving the consensus can require qualifying again, and the other HSDir requirements still apply. |
| Authority protocol requirements | Tor 0.4.8 and earlier no longer satisfy the new required protocol capabilities. Upgrade promptly; do not interpret this as a promise that a new binary immediately gains consensus flags. |

Upstream also fixes middle-only flag handling, a control-port HSPOST memory leak, Conflux stream attachment and scheduling behavior. Directory parsing/logging and connection-list handling are improved; fallback directories and GeoIP data are refreshed. These are upstream Tor changes, not new container services.

Upstream's [corrected release notes](https://gitlab.torproject.org/tpo/core/tor/-/blob/407ccd28a2d0ebeb18f66cc7e8db76e178218e05/ReleaseNotes) also record **TROVE-2026-072**, a directory-authority bug that could prevent a valid consensus, a channel-padding timeout fix that prevents repeated warnings/padding, and a client fix that reconsiders an exit after a new consensus. These entries were omitted from the original tagged notes. The [tag-to-correction comparison](https://gitlab.torproject.org/tpo/core/tor/-/compare/tor-0.4.9.15...407ccd28a2d0ebeb18f66cc7e8db76e178218e05) changes release documentation and version metadata, not runtime source. Builds continue to use the authenticated 0.4.9.15 archive, never the moving development branch.

These defenses mitigate directory-request abuse; they do not guarantee that attack traffic, circuit creation or CPU load disappears. Check notice/heartbeat output and host resource use after rollout.

## 📝 What to change in torrc

**There are no new mandatory torrc lines.** The samples and ENV-generated torrc document the settings without forcing thresholds. Tor's defaults allow the consensus to adjust defenses:

| Option | torrc default | Fallback when consensus does not specify it |
| --- | --- | --- |
| `DoSBeginDirRateEnabled` | `auto` | Enabled (`1`) |
| `DoSBeginDirRate` | `0` (follow consensus) | 10 BEGIN_DIR requests per second, per circuit |
| `DoSBeginDirBurst` | `0` (follow consensus) | Burst of 60 |
| `DoSBeginDirDefenseType` | `0` (follow consensus) | `3`, close the circuit |

Leave these four options **unset**, as requested in the upstream operator announcement. `DoSBeginDirLimitEnabled` is a consensus parameter with no matching torrc option. The HSDir request defense has no operator enable switch.

If you added **`DirCache 0`** as a temporary attack workaround, upgrade the binary first, then review removing that override and observe the relay. Disabling directory caching also opts out of directory-cache, fallback-directory, Guard and HSDir roles. `DirPort 0` is a different option: it disables the standalone directory listener and should not be removed as part of this change.

Preserve intentional provider restrictions and deployment-specific settings. Mounted torrc files and includes remain operator-owned; this update never rewrites them automatically. Edit the mounted host file, or the persistent ENV source for generated configs, validate it, and use `refresh` for subsequent configuration-only reloads. Recreating the container is required to replace Tor itself.

## 🏗️ Authenticated upstream source builds

Both variants build Tor **0.4.9.15** from the authenticated upstream release, independently of Alpine's Tor package availability. Alpine still supplies the stable/edge base and runtime libraries. The reviewed [source lock](https://github.com/r3bo0tbx1/tor-guard-relay/blob/v2.2.1/build/tor/source.json) records the exact version, SHA256 and release-signing fingerprint; source verification, component checks and published-image monitoring use that same security floor.

The build verifies the signed upstream checksum in an isolated keyring, checks the pinned checksum and hashes the archive before extracting or compiling it. Each target uses matching Alpine builder/runtime bases and runs upstream tests. Tor is installed as a locally signed APK, with GeoIP data, license, runtime dependency metadata and `/usr/share/tor/source.json`; no old Tor package is installed and overwritten. Compilers and private package-signing material stay in the builder stage. All four candidates still require acceptance, recovery, source/image security scans and retained SBOM/provenance evidence before publication.

Candidate workflows use native AMD64/ARM64 hosts and verify the Docker host architecture. Local full-system ARM64 Linux VMs can also supply the required target kernel. QEMU user-mode emulation cannot validate the upstream seccomp sandbox tests; a failing emulated build does not satisfy the ARM64 gate. Sandbox tests and support remain enabled. See the [local testing requirements](https://github.com/r3bo0tbx1/tor-guard-relay/blob/v2.2.1/docs/LOCAL-TESTING.md#environment).

As of **29 October 2026**, Alpine's stable/edge indexes still offered **0.4.9.14-r0** on both architectures. This release replaces the package-availability gate with authenticated source packaging. No build lowers the minimum, mixes Alpine branches or silently switches between package and source origins.

## 🔄 Future Tor updates under v2.2.1

The **🔒🧅** schedule checks the official distribution index every six hours and on manual dispatch. It ignores prereleases, refuses downgrades and leaves an equal pin unchanged. A newer stable release is authenticated and retained as a proposed source lock, with a failing watch check requesting maintainer review. Discovery or authentication failures never change the pin.

Prepare the next compatible Tor security update locally:

```sh
python3 scripts/release/update-tor-source.py --output /tmp/tor-upstream.json
# Replace the example with an actually published stable version.
python3 scripts/release/update-tor-source.py --version 0.4.9.16 --write
```

Review the verified pin, upstream changes and operator guidance; pass all candidate gates; then merge and publish a reviewed main rebuild. The project can remain **2.2.1**, refreshing its existing image tags while preserving the immutable Git `v2.2.1` tag. The rebuilt images record their actual main source SHA; use digest references to retain an exact build. Scheduled rebuilds use the merged source pin and do not adopt unreviewed upstream binaries automatically. Operator-visible compatibility changes warrant a new project release. See the [source-build and update guide](https://github.com/r3bo0tbx1/tor-guard-relay/blob/v2.2.1/build/tor/README.md).

## 📦 Included main-branch maintenance

This release includes Snowflake **2.15.3**, KCP **5.7.1**, SMUX **1.5.58** and the Renovate validator **44.197.1**. The validator's Node compatibility rule and routine PR creation window are retained. The Go builder and independently reviewed Lyrebird source pin remain unchanged. Publication requires the complete candidate gates to pass with this combined source; validation of a preceding main commit cannot substitute for that evidence.

The startup banner now reads the actual image build version. Bridge/exit diagnostics and `bridge-line` resolve Tor's effective configuration, including options in torrc includes. The offline upgrade rehearsal checks guard, exit and bridge identities, family/transport keys, mounted configuration, ENV regeneration and current-run readiness against existing v2.2.0 images.

## 🔄 Required operator migration

All guard, middle, exit and bridge deployments should migrate promptly to validated published images containing Tor 0.4.9.15 or newer. The project cannot replace remote containers automatically. Use one relay at a time:

1. Record its fingerprint, image digest, Compose file, torrc/includes, family keys and bridge state. Create and verify an [encrypted backup](https://github.com/r3bo0tbx1/tor-guard-relay/blob/v2.2.1/docs/BACKUP.md); keep a staged restore available.
2. Confirm that the chosen **published digest** contains Tor 0.4.9.15 or newer and has passed the stable/edge AMD64/ARM64 candidate gates. Version tags alone do not establish the Tor version of a running container.
3. Review any temporary `DirCache 0` override. Keep the four new rate-limit settings unset. Validate the deployment and configuration with the new image before activation.
4. Pull the validated image and recreate only the intended Compose service, retaining its data, keys, configuration and include mounts. Never run two copies of one relay identity and never delete volumes to upgrade.
5. Verify `tor --version`, the unchanged fingerprint, valid configuration, current-run health and fresh bootstrap evidence. Check external reachability separately and observe load/heartbeat changes.
6. Keep the encrypted backup and rollback deployment until verification completes. Update the [fleet protection review](https://github.com/r3bo0tbx1/tor-guard-relay/blob/v2.2.1/docs/REGISTRY-RETENTION.md#-discover-deployed-image-identities-safely) with the actual deployed identities before any registry retirement.

For an existing Compose service, replace `<service>` with its actual name and use the validated image reference in the Compose file:

```sh
docker compose pull <service>
docker compose up -d --no-deps --force-recreate <service>
docker compose exec <service> tor --version
docker compose exec <service> config validate
docker compose exec <service> fingerprint
docker compose exec <service> doctor --json
```

Capture the old fingerprint and verify recovery **before** running the pull/recreate steps. A passing `--verify-config` does not prove public reachability. A successful `refresh` does not replace the binary.

## 📊 Optional observation

When an operator already uses a privately bound MetricsPort, the new counters are:

```text
tor_relay_dos_total{type="begindir_rate_rejected"}
tor_relay_dos_total{type="begindir_rejected"}
tor_relay_dos_total{type="begindir_hsdir_rejected"}
```

The DoS heartbeat also reports these refusals. This release does not enable or expose MetricsPort, change health JSON fields or convert a mitigation counter into a readiness condition.
